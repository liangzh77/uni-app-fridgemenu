# uni-app冰箱菜单应用宪章

## 核心原则

### 一、组件化优先 (Component-First)

所有功能必须以可复用组件的形式实现。组件必须具备：
- 独立性：每个组件自包含，可独立测试和文档化
- 明确目的：拒绝仅为组织代码而创建的组件
- 接口清晰：通过props和events定义清晰的输入输出契约

**原理**: 组件化架构提高代码复用性，降低维护成本，符合uni-app跨平台开发的最佳实践。

### 二、数据优先 (Data-First)

功能设计从数据模型开始，而非界面：
- 必须先定义数据结构和状态管理方案
- 使用Vuex/Pinia进行集中式状态管理
- 数据持久化策略（本地存储/云端同步）必须明确

**原理**: 清晰的数据模型是应用稳定性的基础，避免因界面驱动导致的数据混乱。

### 三、测试先行 (Test-First) - 非强制性

鼓励但不强制TDD实践：
- 新功能优先编写测试用例
- 关键业务逻辑必须有单元测试覆盖
- 跨端兼容性测试（H5/小程序/App）

**原理**: 测试保证代码质量，尤其在跨平台开发中减少平台特定bug。

### 四、用户体验一致性 (UX Consistency)

跨平台界面必须保持一致的用户体验：
- 统一的UI组件库和设计规范
- 响应式布局适配不同屏幕尺寸
- 遵循各平台的交互规范（微信小程序、支付宝小程序、H5等）

**原理**: 一致的体验提升用户满意度，降低学习成本。

### 五、性能与优化 (Performance & Optimization)

关注应用性能和资源占用：
- 图片必须压缩和懒加载
- 列表渲染使用虚拟滚动
- 网络请求必须有loading状态和错误处理
- 小程序包体积控制在2MB以内（主包）

**原理**: 移动端设备资源有限，性能直接影响用户留存。

## 技术约束

### 开发技术栈
- **框架**: uni-app (Vue 3组合式API优先)
- **状态管理**: Pinia (推荐) 或 Vuex
- **UI组件库**: uni-ui 或自定义组件
- **编程语言**: JavaScript/TypeScript (推荐TypeScript)
- **目标平台**: 微信小程序、H5、App (Android/iOS)

### 代码规范
- 遵循Vue 3风格指南
- 使用ESLint + Prettier进行代码格式化
- 组件命名采用PascalCase，文件名使用kebab-case
- 必须编写中文注释说明关键逻辑

### 数据安全
- 用户隐私数据必须加密存储
- API请求必须使用HTTPS
- 敏感操作需要用户授权
- 遵守《个人信息保护法》和平台规范

## 开发流程

### 功能开发流程
1. **需求分析**: 编写功能规格说明 (spec.md)，包含用户场景和验收标准
2. **设计阶段**: 创建实施计划 (plan.md)，定义数据模型和组件结构
3. **实现阶段**: 按任务列表 (tasks.md) 逐步实现
4. **测试验证**: 跨端测试，确保各平台功能正常
5. **代码审查**: 检查代码规范和宪章合规性

### 分支管理
- `main`: 生产分支，只接受经过测试的合并
- `dev`: 开发分支，日常开发基准
- `feature/###-功能名`: 功能分支，格式如 `feature/001-food-list`
- `bugfix/###-问题描述`: 修复分支

### 提交规范
遵循约定式提交 (Conventional Commits)：
- `feat`: 新功能
- `fix`: 问题修复
- `docs`: 文档更新
- `style`: 样式调整（不影响逻辑）
- `refactor`: 重构
- `perf`: 性能优化
- `test`: 测试相关

## 治理规则

### 宪章权威性
本宪章优先于所有其他开发实践和规范。所有代码审查和合并请求必须验证宪章合规性。

### 修订流程
1. 提出修订建议，说明原因和影响范围
2. 团队审查并达成共识
3. 更新宪章版本号（遵循语义化版本）
4. 同步更新所有依赖模板和文档
5. 通知所有开发人员

### 复杂度管理
任何增加系统复杂度的决策必须书面说明：
- 为何需要该复杂度
- 为何更简单的方案不可行
- 记录在实施计划的"复杂度跟踪"表格中

### 合规性审查
每次代码审查必须检查：
- [ ] 是否遵循组件化原则
- [ ] 数据模型是否清晰定义
- [ ] 跨平台兼容性是否考虑
- [ ] 性能影响是否评估
- [ ] 代码注释是否完整（中文）
